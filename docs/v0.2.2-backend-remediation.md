# SouthRail v0.2.2 backend correctness and reliability remediation

## Verdict: NOT SAFE TO MERGE UNTIL UPDATED CI PASSES

This focused change addresses the critical and high findings from the post-v0.2.1 audit without beginning v0.3 or introducing distributed infrastructure. PR #44's original GitHub Actions run passed all 52 tests, but the updated branch now includes additional FIFO and PostgreSQL coverage. It must not be declared safe to merge until that updated Maven/Testcontainers suite passes in CI.

## Root causes and fixes

### Queue gaps, uniqueness, and promotion

- **Root cause:** Queue positions used active booking count rather than maximum/serialized allocation. Cancellation removed a row without resequencing and never consumed newly available confirmed/RAC capacity.
- **Files changed:** `BookingService`, `BookingCancellationService`, `BookingRepository`, `PassengerRepository`, migrations `005` and `006`, and booking regression tests.
- **Locking strategy:** Creation and cancellation acquire the same pessimistic train-row lock before inventory or queue mutation. Cancellation then locks the booking and queue rows. The train lock serializes every train/date/class decision conservatively (the existing model has no date/class inventory lock row) and avoids duplicate assignments.
- **Before:** `count(status) + 1`; cancellation left gaps; no promotions.
- **After:** New entries use `max(queue_position) + 1` while holding the train lock. Cancellation temporarily shifts a queue by 1,000,000, clears the persistence context, and rewrites deterministic FIFO positions from 1, avoiding immediate partial-unique-index collisions. Ordering is queue position, creation time, PNR, then ID.
- **Promotion:** Released seats promote whole RAC parties from the head only when the full party fits, preserving FIFO and the booking-level status model. Resulting RAC vacancy promotes whole waitlist parties in order when the full party fits. Passenger statuses, reservation labels, queue positions, and physical seats change in the same transaction.
- **Passenger capacity:** RAC occupancy is now the number of RAC passengers, not booking rows. A new party enters RAC only when the complete party fits the remaining ten-passenger capacity; otherwise it enters waitlist. No arbitrary passenger-list limit was added.

### Account-token issuance

- **Root cause:** Invalidation and insertion were serialized only by transaction boundaries, which do not prevent two transactions from observing the same open-token state.
- **Files changed:** `UserRepository`, `AuthService`, and migration `006`.
- **Strategy:** Reset, verification-resend, unlock, and restored-account issuance lock the owning user row before throttling, invalidation, and hashed-token insertion. A partial unique index on `(user_id, token_type) where used_at is null` is the final database invariant. Migration `006` consumes older duplicate open tokens before creating it. Existing token-consumption pessimistic locking remains unchanged.

### Login attempt concurrency

- **Root cause:** Login loaded and saved an unlocked detached account across separate repository transactions, allowing lost updates.
- **Files changed:** `UserRepository`, `AuthService`, and regression tests.
- **Strategy:** The complete authentication state transition runs in one transaction and locks the user row. `ApiException` is explicitly non-rollback so invalid-attempt increments and the fifth-attempt lock persist. Successful authentication resets the same locked row before issuing tokens.

### Transaction-safe email

- **Root cause:** SMTP rendering and delivery ran synchronously inside account and booking transactions, including while the train lock was retained.
- **Files changed:** `EmailNotificationService` and its new tests.
- **Strategy:** Enabled email registers a Spring transaction synchronization. Delivery runs only in `afterCommit`; rollback invokes no delivery. Delivery exceptions are contained and logged after commit, so committed business state is not rolled back or presented as failed. Calls made without an active transaction remain best-effort synchronous. This intentionally uses no outbox/Kafka in v0.2.2.

### Runtime feature flags and directly related hardening

- **Root cause:** Feature flags were consulted only by production startup validation, not by the integration services.
- **Files changed:** `AiAssistantService`, `EmailNotificationService`, `SecurityConfiguration`, `SouthRailSecurityProperties`, and AI/email tests.
- **Behavior:** Disabled email schedules and performs no mail operation. Disabled AI rejects before calling Gemini. Gemini endpoints now require authentication, preventing anonymous quota use. JWT access lifetime is bounded to 1,440 minutes and refresh lifetime to 90 days while retaining positive-value validation. Production credential validation remains intact.

## Database migration and constraints

- `005_booking_concurrency.sql` no longer treats a booking queue position of ten as RAC capacity; that rule was incorrect for multi-passenger bookings.
- New idempotent `006_queue_and_token_concurrency.sql` repairs legacy passenger-based RAC overflow into waitlist, resequences affected queues without unique collisions, synchronizes passenger statuses, consumes duplicate open account tokens, and adds the single-open-token partial unique index.
- Existing RAC/WL partial unique indexes and positive/non-null queued-position check remain in force.

## Remaining risks

1. The current train lock intentionally serializes more than necessary because inventory has no journey/class lock record. It is correct but may limit throughput for very busy trains.
2. Parties are indivisible under the existing booking-level queue model. A head party that does not fit blocks smaller later parties rather than violating FIFO; passenger-level mixed booking states would require a broader domain redesign.
3. Post-commit email remains best-effort with no durable retry, as explicitly required for this phase. Failures are logged but can lose a notification.
4. Migration `006` is now exercised by a PostgreSQL Testcontainers test, but that test still requires a successful updated CI run and the migration should also be tested against sanitized production-shaped data before rollout.
5. Account enumeration behavior was reviewed but not changed because normalizing all registration/recovery responses is a wider API/UX contract change; deploy edge rate limits in addition to the database-safe account locks.

## Existing database upgrade path

Fresh Compose initialization executes every numbered file in `database/`, including `006_queue_and_token_concurrency.sql`, for a new empty volume. Existing databases must not rely on that initialization hook. During a maintenance window, operators must back up the database, stop backend writers, and run `deploy/upgrade_v0.2.2.sh` with `DATABASE_URL`; the helper applies `004`, `005`, and `006` in order in one `psql` transaction with stop-on-error behavior. Full operator commands are in `docs/DEPLOYMENT.md`.
